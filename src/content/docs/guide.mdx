忘记怎么开口时，回到这里。把决定和观察写具体，比背下某个“万能提示词”更有用。

## 需求单五问

1. **给谁看？** 谁来用，看完要做什么。
2. **必须有？** 哪些内容与行为不可缺。
3. **这次不做？** 限制复杂度；已有项目还要写不能动什么。
4. **怎样算做完？** 可以观察和重复检查的标准。
5. **还不确定？** 用占位或先提问，不让 Agent 猜经历与数据。

顺序是：**写需求单 → 让 Agent 给计划 → 检查冲突 → 允许修改**。需求单写完后留着，后续每次验收都要回看。

## 反馈四要素

**在哪里 → 看到什么 → 想改成什么 → 哪些别动。**

能给出复现步骤就更好。比如“新建带备注的任务 → 勾选完成 → 备注消失”，比“备注有 bug”更容易处理。

## 三种常见偏差

| 现象 | 先检查 | 处理 |
| --- | --- | --- |
| 出现了计划外的文件 | 需求单的“这次不做” | 让 Agent 列出改动，撤回无关部分 |
| 页面能打开，内容不对 | 需求单的“必须有” | 给出位置、看到的结果、期望结果 |
| 修好一处，弄坏另一处 | 原有功能的回归检查 | 缩小改动范围，再验证一次 |

## 分清四种状态

| 状态         | 看什么才算数                         |
| ------------ | ------------------------------------ |
| Agent 回复了 | 对话中有响应；还不能证明文件存在     |
| 文件保存了   | 文件区找到文件，打开能看到内容       |
| 程序跑起来了 | 终端有服务地址，浏览器能打开实际页面 |
| 结果验证过了 | 对照需求、审查 Diff、检查新旧功能    |

这四种状态不能互相代替。网页能打开，也可能在手机上溢出。

## 版本与改动

**提交** 是保存一个可回看的代码版本。先记下能运行的初稿 v1，再改动和验收，最后记下 v2。

**差异** 显示两个版本之间增删了什么。检查文件是不是都在计划里、有没有改无关内容。新文件尚未追踪时 `git diff` 通常不会显示它；先在文件区检查，再用 `git add` 暂存和 `git diff --staged` 审查。

**回归检查** 是再试一次原有功能，确认加了新功能没有弄坏旧功能。

## 术语不用背

- **终端**：输入命令的地方，执行前先看当前目录。
- **依赖**：项目要用的现成工具或代码。
- **本地服务器**：把文件通过一个本机地址提供给浏览器，不会发布到互联网。
- **接口**：前端向后端请求或保存数据的入口。
- **数据库**：持久保存数据的地方。页面上出现了内容，不代表已写进数据库。
- **交付**：提供能继续用的文件、运行说明、检查结果和待替换项；不只是聊天里说“做好了”。
