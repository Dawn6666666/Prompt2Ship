# 06 · 案例二：给 Todo 应用加备注（在已有项目里改）

## 为什么要有第二个案例

案例一从空文件夹开始，每一行代码都是 Agent 新写的。真实学习和工作中更常见的是：**在别人（或者以前的自己）写好的项目里加一个功能。**
这时最大的风险是 Agent 改了不该改的地方。案例二用同样的五步，重点练两件事：

1. **先读懂再动手**——需求分析的前置动作是了解现有项目。
2. **控制修改范围**——“这次不做”变成“哪些不能动”，检查阶段要确认“只改了该改的”。

## 概要

| 项 | 内容 |
|---|---|
| 路由 | `/case/todo/` |
| 起点 | 一个能运行的 Todo 应用（React 前端 + Express 后端 + SQLite），有分类、优先级、筛选、拖拽 |
| 需求 | 给任务加“备注”：新建和编辑时可填写，列表中显示，可清空 |
| 核心情节 | 先只读了解项目 → 写需求单（含不能动的范围）→ 确认计划只改 4 个文件 → 生成并运行 → 发现“勾选完成后备注被清空” → 描述复现步骤 → Agent 只改更新接口 → 原有功能回归检查 → 提交 |
| 素材 | 沿用 `data/todo.ts`、`todo-flow.ts`、`todo-evidence.json`、`verify-todo.mjs`，按新五步重组 |

> 现有 7 阶段（understand/plan/database/api/frontend/flow/verify）合并为 5 步。数据库/接口/前端三层改动合并为第 3 步的“改动地图”，不再各占一个阶段。

## 对新手的降压措施

- 页首明确：“这个案例的代码你不需要全部看懂。你要学会的是：怎么让 Agent 帮你看懂，以及怎么确认它没有乱改。”
- 每段代码只显示与备注相关的 3–8 行，其余折叠为“…原有代码不变…”。
- 名词第一次出现时给一句话解释并加入术语表：前端、后端、接口、数据库。
- 提示词全部改写为短句、分行，去掉一长串文件路径（路径由 Agent 在计划中给出，读者只需确认）。

---

## 第 1 步 · 想清楚（先读懂现有项目）

**这一步做什么**：先让 Agent 介绍项目，再写一份标明“不能动”的需求单。
**怎样算完成**：你能说出“备注要存在哪里、在哪里显示”；需求单里写了不能改动的功能。

1. **只读提问**（场景：Agent 面板 + 文件区）

```
请先阅读这个项目，用简单的话告诉我：
1. 任务数据保存在哪里？
2. 新建任务时，数据从页面到保存经过了哪些文件？
不要修改任何文件。
```

2. Agent 回复一张**项目地图**（复用 TodoFlow 的节点）：`页面表单 → 前端请求 → 后端接口 → 数据库`，每个节点标出文件名。文件区中对应文件同步高亮。场景标注：“文件没有变化——这次只是读。”
3. **五问（已有项目版）**，用需求拆解器的同一组件，选项换成本案例：

| 问 | 示例回答 |
|---|---|
| 解决什么问题 | 任务标题太短，想记下细节（如“带学生证”） |
| 必须有 | 新建和编辑时能填备注；列表中显示；可以清空；刷新后还在 |
| 不能动 | 分类、优先级、筛选、拖拽排序保持不变；不换框架、不重写项目 |
| 怎样算做完 | 新建带备注的任务，刷新后仍显示；勾选完成后备注还在；原有四个功能照常 |
| 还不确定 | 旧任务没有备注怎么办 → 请 Agent 给方案 |

4. 生成提示词（短句分行，末尾仍是“先给计划，不要写代码”）。

## 第 2 步 · 定计划

**这一步做什么**：确认 Agent 打算改哪些文件、每个文件改什么。
**怎样算完成**：计划只涉及 4 个文件，并说明了旧数据怎么处理。

- 场景：Agent 回复计划 + 文件区。计划中的每个文件在文件区标出“将修改”（橙色），其余文件保持灰色。
- 计划（预设）：数据库加一列（旧任务默认空备注）；新建/更新接口接收备注；表单加输入框；列表显示备注。
- 交互：读者在文件区点击“将修改”的文件，看到计划中对应的一句说明。
- 教学要点：**计划里没提到的文件，就不应该被改。** 第 5 步会用它来检查。
- 处理“还不确定”：Agent 的计划回答了“旧任务默认空备注”，需求单该行打勾。

## 第 3 步 · 生成并运行

**这一步做什么**：让 Agent 按计划修改，运行项目，在页面上试一次。
**怎样算完成**：页面能新建带备注的任务，刷新后还在。

- 场景：**改动地图**为主体——四个节点（数据库 / 接口 / 表单 / 列表）横向排列，点击节点在下方显示该文件的局部 Diff（复用 `todoChanges` 数据，每段只显示关键行）。
- 每个节点上有状态点：文件保存了（蓝）。
- 运行：终端 `npm run dev`，输出前后端地址；预览显示 Todo 页面。
- 读者在预览中“新建任务（带备注）→ 刷新”，备注仍在。状态条点亮“程序跑起来了”。
- 提交 `git commit -m "增加任务备注"`。

## 第 4 步 · 发现问题并修改

**这一步做什么**：做一次原有功能的操作，发现备注被清空，写出可复现的反馈。
**怎样算完成**：勾选完成后备注仍在；修改只涉及更新接口。

- 情节：读者在预览中勾选“完成”某个带备注的任务 → 备注消失。（对应现有数据中“不传与清空，是两件不同的事”的知识点，v1 故意保留这个缺陷）
- 需求单中“勾选完成后备注还在”一行闪烁。
- 数据流演示（复用 TodoFlow）：点“勾选完成”，请求只带了 `completed`，接口把没传的 `notes` 当成空值写入数据库。节点逐个点亮，在“接口”节点出现红色标记。
- 反馈练习（与案例一相同的形式，三选一），好反馈示例：

```
复现步骤：新建一个带备注的任务 → 勾选完成 → 备注消失。
期望：勾选完成时备注保持不变；只有在编辑时主动清空才清空。
请只修改更新接口，不要改动前端和数据库。
```

- Agent 修改后 Diff 仅在 `server/routes/todos.js` 的 PUT 部分；切换修改前/修改后，数据流动画对比。

## 第 5 步 · 检查并交付

**这一步做什么**：确认新功能可用、原有功能没坏、改动没有超出计划。
**怎样算完成**：功能检查和回归检查全部通过；改动文件与计划一致。

- **功能检查**（来自需求单“必须有/怎样算做完”）：新建带备注、编辑、清空、刷新后仍在、勾选完成后仍在。
- **回归检查**（来自需求单“不能动”）：分类、优先级、筛选、拖拽。
- **范围检查**：`git diff --stat` 输出的文件列表与第 2 步计划对照，四个文件全部对上，标绿。
- 真实证据：保留 `todo-evidence.json` 与浏览器截图，标注“这些是我们在真实项目中运行检查得到的结果”，说明由 `verify-todo.mjs` 生成。示例结果与读者勾选分开。
- 交付：提交信息示例；完整项目下载/仓库链接；“跟做方式”折叠（原 TodoFollowAlong）。

## 回顾：两个案例对照

案例末尾放一张对照表，强化“同一套五步”：

| 步骤 | 案例一（新建） | 案例二（修改） |
|---|---|---|
| 想清楚 | 五问 → 需求单 | 先读懂项目，再五问，重点是“不能动” |
| 定计划 | 发现与需求冲突的方案 | 确认只改 4 个文件 |
| 生成并运行 | 文件出现，网页打开 | 改动地图，页面试用 |
| 发现问题并修改 | 手机端溢出 | 勾选完成后备注被清空 |
| 检查并交付 | 对照需求单 | 功能 + 回归 + 范围三类检查 |
