# 01 · 现状诊断

本篇列出现有网站和提纲中需要改的地方，按严重程度排序。每条都说明“为什么是问题”，后续分册给出具体改法。

---

## 一、定位与内容层面

### 1.1 需求分析分量太轻（最严重）

- 现状：需求分析在案例一里只占一个阶段“描述需求”，右侧是一张小字的需求文档，左侧是一段已经写好的提示词。在学习路线里只有 `workflow/first-task` 一页，`WorkflowScene` 的“目标/内容/边界/验收”拼装器也只是把四个文本块拼到一起。
- 问题：新手看到的是一份**写好的成品**，看不到这份需求是**怎么从一句模糊的话变出来的**。他们学到的只是“提示词要写长一点”，学不会怎么想。
- 用户明确要求“特别是需求分析这个过程要着重讲讲”，现在的设计没有回应这个要求。
- 改法见 `03-requirements-analysis.md`。

### 1.2 人物和场景离读者太远

- 案例一的人物是“林间，杭州的独立设计师”，作品叫“山野手记”“留白工作室”。大一学生很难代入，也很难用同样思路描述自己。
- `WorkflowScene` 中的示例又换成了“大学生个人网站”，人物前后不一致。
- 改法：统一为一位大一学生，内容是课程作业、社团项目和联系方式，读者可以直接替换成自己的信息。

### 1.3 名称、工具、命令前后不统一

| 位置 | 项目文件夹 | 运行方式 |
|---|---|---|
| 编辑器导览 EditorTour | `my-first-site` | — |
| 案例一 | `lin-portfolio` | `python3 -m http.server 4322` / `py` |
| 提纲 | `ai-coding-mvv` | 未定 |
| 案例二 | `todo-app-p2s` | `npm` |
| 运行环境页 | — | 同时检查 Python 与 Node |

- 问题：新手每换一次名字都会怀疑“是不是我做错了”。Python 和 Node 两套运行方式会让准备阶段的安装量翻倍。
- 改法：案例一文件夹统一 `my-homepage`，运行统一 `npx serve .`（Node 自带 npx，案例二本来也要 Node）。准备篇只检查 Node、Git、VS Code、Agent 四项。

### 1.4 提纲中不合理的地方

| 提纲原文 | 问题 | 调整 |
|---|---|---|
| 目录名 `ai-coding-mvv` | “MVV”是内部术语，学生看不懂，也不是他们会起的名字 | 改为 `my-homepage` |
| 标题“AI Coding 工作台的最小可用验证” | 工程化表述，读者不知道这一节在干什么 | 改为“开工检查：确认工具都能用” |
| 用“生成一个 HTML 页面的基本结构”验证 Agent | 会让 Agent 直接写文件，污染还没开始的项目；而且和后面“先计划再生成”的教学冲突 | 改为只读任务：“看看当前文件夹里有什么，用一句话告诉我” |
| 先 `git init` 再打开 VS Code | 新手更自然的顺序是：建文件夹 → 用 VS Code 打开 → 在集成终端里执行命令。这样所有命令都在一个窗口完成 | 调整顺序，终端统一用 VS Code 集成终端 |
| 七个阶段 | “验证修改”和“完成交付”边界模糊；“描述需求”和“制定计划”对新手区别不大但被拆开 | 合并为五步，见 `05-case-homepage.md` |
| 每个动态都要答“目标/操作/变化/依据” | 方向正确，但如果每一屏都铺开四块文字，页面会非常重 | 保留四要素作为**设计检查表**；界面上只显示“这一步做什么”和“怎样算完成”，“变化”由场景本身表现 |
| “示例检查结果”与“我已在本机完成”分开 | 方向正确 | 保留，并统一为两种视觉：灰色“示例结果”标签 / 用户自己勾选的“我做到了” |
| 下载完整 HTML 作为交付 | 交付物还应包含“我替换了哪些内容”的清单，否则学生会直接交一份别人的主页 | 交付卡片加“替换清单” |

### 1.5 案例二对新手过重

- 案例二的提示词很长，充满文件路径；7 个阶段包括数据库、API、前端、数据流，对大一下的同学跨度过大。
- 但“在已有项目里改功能”是非常有价值的第二课：它教会“先读懂再动手”和“控制修改范围”。
- 改法：保留案例，但收缩为同样的五步，把数据库/API/前端合并到“生成并运行”中用一张“改动地图”表现，重点放在需求分析阶段的“读懂现有项目”和检查阶段的“只改了该改的”。见 `06-case-todo.md`。

## 二、信息架构层面

### 2.1 入口太多，路线不清

- 首页同时出现：英文 kicker、三步预览 HeroDemo、四章学习路线、两个案例卡片、结尾 CTA。读者不知道该先点哪个。
- 导航“学习路线 / 交互案例（下拉）/ 方法速查”与首页卡片重复。
- 改法：首页只有一个主按钮“从准备开始”，其余都是路线图上的节点。见 `02-architecture.md`。

### 2.2 学习路线与案例割裂

- 学习路线（Starlight 文档）讲“首个任务、运行反馈、Git”，案例又把同样的内容演一遍，两边内容重复但例子不同。
- 改法：学习路线只保留**准备篇**（安装与检查）；工作流的讲解直接放进案例里，在案例中第一次出现时讲透。方法速查页收集所有要点，供回看。

### 2.3 “动态 NN”编号

- 全站从 01 编到 20，案例一是“动态 07–13”。读者看到“动态 07”会以为自己漏了前面 6 个。
- 改法：删掉全站编号，在案例内使用“第 2 步 / 共 5 步”。

## 三、交互层面

### 3.1 工作台主次颠倒

- 桌面端：左侧 330px 说明栏放大号提示词，右侧产物区经常是一张小字文档，首屏看不到“变化”。
- 手机端：说明先堆叠，产物（网页预览、代码）被挤到很远的下方。
- 改法：场景优先，见 `07-workbench.md`。

### 3.2 “完成”没有依据

- 验证阶段的检查清单全是灰色圆圈，没有通过/未通过的区别；自动播放结束也不会提示读者“你本机还没做”。
- 改法：每个检查项显示“检查了什么 → 看到了什么 → 结论”，示例结果和读者自检分开。

### 3.3 SSR 闪烁

- `useStage` 在服务端渲染第 0 阶段，客户端读取 hash/localStorage 后再切换，打开 `#run` 时会先闪一下第一阶段。
- 改法：阶段切换改为 URL 查询参数或客户端渲染前隐藏内容，见 `10-roadmap.md` 技术部分。

### 3.4 自动播放

- `usePlayback` 每 3.5 秒自动切换，读者读不完就跳走了。新手需要自己控制节奏。
- 改法：默认不自动播放；只在首页 Hero 预览中使用自动播放。

### 3.5 Agent 回复被藏起来

- Agent 的回复放在 `<details>` 里，默认折叠。但“看 Agent 回了什么、和实际文件对照”正是关键教学点。
- 改法：Agent 回复作为场景的一部分直接显示，并标出“回复 ≠ 文件已保存”。

## 四、视觉层面

### 4.1 字号过小、层级过多

样式审计结果：

| 字号 | 出现次数 |
|---|---|
| 6–8px | 24 |
| 9px | 32 |
| 10px | 51 |
| 11px | 46 |
| 12px | 31 |
| 13px | 28 |
| 14px | 22 |

- 小于 12px 的字号出现 150 多次。中文在 10px 以下几乎无法阅读，在手机上更糟。
- 改法：只保留 6 级字号，最小 12px（仅用于代码行号与辅助标签），正文 16px。见 `08-visual-system.md`。

### 4.2 圆角、边框、灰色块过多

- 圆角有 3/4/5/6/7/8/10/12px 共 8 种；几乎每个区域都套了边框卡片，检查点用灰色底条，页面显得“盒子套盒子”。
- 改法：圆角只用 6px（控件）和 12px（容器）两种；减少嵌套卡片，用留白和分隔线组织。

### 4.3 英文装饰标签

- “AN INTERACTIVE GUIDE TO AI CODING”“CASE STUDY / 01”“PROJECT BRIEF / 01”“READY TO HAND OVER”等等宽英文小标签，对中文读者增加了阅读负担，也不传递信息。
- 改法：全部删除或换成有信息量的中文短标签（如“案例一 · 个人主页”）。

### 4.4 样式文件过大

- `teaching.css` 2823 行、363 个顶层选择器，`global.css` 713 行，`completion.css` 539 行。大量一次性样式，难以维护，也导致视觉不一致。
- 改法：组件化重写，按组件拆分 CSS 或改用 Tailwind 工具类 + 少量设计令牌。
