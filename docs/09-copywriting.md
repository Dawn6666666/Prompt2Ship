# 09 · 文案规范与术语

## 一、写给谁

一位大一下学期的同学：学过一点 C 或 Python，知道“文件”和“文件夹”，可能没用过终端，没听说过“部署”“依赖”“接口”。
他们会紧张、怕做错，看不懂时容易放弃。

## 二、语气

- **直接说要做的事**：“打开终端，输入下面这行”，而不是“接下来我们将要进行终端操作”。
- **用“你”**，不用“我们”“读者”“用户”“同学们”。
- **短句**。一句话不超过 35 个字；一段不超过 3 句。
- **先结论后原因**：“不要把 API Key 发给别人。它相当于你账户的密码。”
- **不吓人、不夸张**：不用“轻松”“只需一步”“魔法”“赋能”“颠覆”。
- **出错是正常的**：在“遇到问题”中使用“如果看到……，通常是因为……”。

## 三、每个步骤的固定文案位

| 位置 | 长度 | 示例 |
|---|---|---|
| 步骤标题 | 2–6 字 | 生成并运行 |
| 这一步做什么 | 1 句，≤ 30 字 | 让文件真的出现在文件夹里，再让网页在浏览器里打开。 |
| 小步提示 | 1 句，动词开头 | 点击文件区的 index.html。 |
| 要点 | ≤ 3 条，每条 ≤ 25 字 | 页面能打开，不等于做完了。 |
| 怎样算完成 | 1–2 句，必须是“能看见的” | 文件区有 index.html；浏览器能打开 localhost:3000。 |

提纲中的“目标 / 操作 / 变化 / 依据”四要素作为写作检查表：写每一小步时确认四项都有，但界面上“变化”由场景表现，不写成文字。

## 四、术语表（全站统一用词）

| 统一用 | 不用 | 第一次出现时的解释 |
|---|---|---|
| Agent | 智能体、AI 助手、编程助手（混用） | 能读写你项目文件、运行命令的 AI 编程工具 |
| 提示词 | Prompt、指令 | 你发给 Agent 的话 |
| 需求单 | 需求文档、Brief、需求说明 | 写清楚“要做什么、不做什么、怎样算做完”的几行字 |
| 验收标准 / 怎样算做完 | 完成标准、DoD | 别人能照着检查的条件 |
| 计划 | 方案、实现方案 | Agent 动手前说明的做法 |
| 文件区 | 资源管理器、文件树 | VS Code 左边显示文件的地方 |
| 编辑区 | 编辑器 | 显示和修改代码的地方 |
| 终端 | 命令行、控制台、Terminal | 输入命令的地方 |
| 预览 | 浏览器窗口 | 看网页效果的地方 |
| 版本 / 提交 | commit、快照 | 用 Git 保存的一份记录 |
| 改动 / 对比 | Diff（首次出现写“改动对比（Diff）”） | 前后两个版本的差别 |
| 运行 | 启动、跑起来（口语可用于状态条） | 让程序开始工作 |
| 示例结果 | 预设结果、演示结果 | 网站演示中的结果 |
| 我做到了 | 已完成、完成练习 | 你在自己电脑上确认过 |

- Vibe Coding：首页出现一次并解释——“用自然语言描述需求，让 AI 写代码，你负责想清楚、检查和决定。”之后统一用“和 AI 一起写代码”。
- 英文工具名保持原样（VS Code、Git、Node.js）。
