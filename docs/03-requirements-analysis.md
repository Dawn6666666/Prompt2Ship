# 03 · 需求分析专章（本次重点）

> 用户原话：“特别是需求分析这个过程要着重讲讲。”
> 这一章说明需求分析教什么、怎么教、用什么交互，以及它在两个案例和速查页中如何出现。

---

## 一、要教会的到底是什么

新手对 AI 说的第一句话通常是：

> 帮我做个个人网站。

这句话的问题不是“太短”，而是**有太多决定没有做**，于是 Agent 会替你做：做成什么风格、放什么内容、用什么技术、做到哪一步算完。结果多半“看起来还行，但不是我要的”，然后陷入反复让 AI 重写的循环。

所以需求分析要教的不是“提示词写长一点”，而是一个**可迁移的思考习惯**：

> **在让 AI 动手之前，先替它做好那些只有你能做的决定，并且写下怎样算做完。**

拆成新手可以记住的五个问题，全站统一称为“需求单五问”：

| # | 问题 | 不想清楚会怎样 | 个人主页的回答 |
|---|---|---|---|
| 1 | **给谁看，看完要做什么？** | AI 只能写一个“通用”页面 | 给实习面试官看，看完能联系到我 |
| 2 | **页面上必须有什么？** | AI 自己编内容，或者塞一堆你不需要的板块 | 名字和一句介绍、两个项目、邮箱 |
| 3 | **这次不做什么？** | AI 擅自加框架、动画、后台、多页面 | 不用框架，只一个 `index.html`，不做暗色模式 |
| 4 | **怎样算做完？** | 无法判断“好了没有”，只能凭感觉 | 电脑和手机上都能完整看到，没有横向滚动条；邮箱链接能点 |
| 5 | **还不确定什么？** | 不确定的地方被 AI 悄悄决定 | 头像先用占位，配色让 AI 给两个方案 |

第 3 问（边界）和第 4 问（验收）是新手最容易漏、也最有价值的两问，在交互中要特别突出。第 5 问教会学生“不确定的事可以交给 AI 提出选项，而不是让它直接决定”。

### 三个配套概念（第一次出现时讲，之后只引用）

1. **需求单 ≠ 提示词**。需求单是你自己想清楚的结果，提示词是把它发给 AI 的方式。先有单子，再有提示词。
2. **验收标准要能“看见”**。“好看”不是标准；“手机上没有横向滚动条”是标准。判断方法：别人能不能照着检查。
3. **需求会变，单子要跟着改**。案例一第 4 步发现手机溢出时，要回到需求单确认“这是不是本来就要求的”——是，所以这是缺陷，不是新需求。

## 二、交互设计：需求拆解器

在案例一第 1 步“想清楚”中，用一个可操作的组件代替现在的“一张写好的需求文档”。

### 2.1 整体流程（4 个小步，读者手动点“下一步”）

```
小步 A：看问题           小步 B：逐问回答            小步 C：看差别               小步 D：变成提示词
"帮我做个个人网站"   →   五问卡片逐个展开      →    两份结果并排对比       →    需求单 → 可复制的提示词
AI 会替你决定哪些？       每问：选择 / 填写            模糊 vs 清楚                  + 先计划再动手的一句话
```

### 2.2 小步 A：看见“被替你决定”的东西

- 左侧显示一句话“帮我做个个人网站”。
- 右侧是一张“AI 需要猜的事情”清单，逐条出现（读者点击“下一条”或一次全部展开）：
  - 给谁看？ → AI 猜：所有人
  - 放什么？ → AI 猜：关于我、技能、经历、博客、联系……
  - 用什么做？ → AI 猜：可能是 React + 多个文件
  - 做到哪？ → AI 猜：不知道，可能一直加
- 每一条旁边标一个小标签“AI 在猜”。
- 结论一句话：**你没做的决定，AI 会替你做。**

### 2.3 小步 B：五问卡片

五张卡片纵向排列，一次只展开一张（手风琴），每张结构一致：

```
┌ 3 / 5  这次不做什么？ ─────────────────────────────┐
│ 为什么要问：不写边界，AI 常常会多做——加框架、加动画、 │
│ 拆成很多文件，你反而看不懂。                          │
│                                                      │
│ 勾选你要排除的（预设选项）：                          │
│ [✓] 不使用框架，只写 HTML 和 CSS                      │
│ [✓] 只生成一个 index.html                             │
│ [✓] 不做暗色模式、不做动画                            │
│ [ ] 不需要联系表单，只放邮箱                          │
│ + 自己写一条                                          │
│                                                      │
│ 写进需求单：                                          │
│ “这次不做：框架、多文件、暗色模式、动画。”            │
└──────────────────────────────────────────────────────┘
```

- 每张卡片包含：问题、为什么要问（一句话）、**可勾选的预设选项**、一个可选的自定义输入、实时生成的“写进需求单”的句子。
- 用勾选而不是空白输入框：新手面对空框不知道写什么；预设选项本身就是在教“这类问题一般有哪些答案”。
- 预设选项中故意放 1 个“诱惑项”（如“加一个炫酷的动画背景”），读者勾选时出现一行温和提示：“第一次可以先不加，能跑起来以后再迭代。”——教会“先做小”。
- 第 4 问（怎样算做完）的选项写成可检查的句子，并有一个“好/不好”的小练习：给出“页面好看”“手机上没有横向滚动条”两条，让读者选哪条是能检查的。
- 右侧（桌面）或底部（手机）实时显示**需求单预览**，每回答一问就多一行，新增的行高亮 1 秒。

### 2.4 小步 C：看差别

并排两栏，同一个场景的两种结果（预设的 Agent 输出摘要 + 页面缩略图）：

| 只说“帮我做个个人网站” | 用需求单 |
|---|---|
| 生成 5 个文件，用了 React | 只生成 `index.html` |
| 有“技能”“博客”等你没有的板块 | 只有介绍、两个项目、邮箱 |
| 内容是虚构的人 | 内容是你给的或明确标注的占位 |
| 不知道是否完成 | 可以逐条检查 4 条验收标准 |

- 这里展示的“模糊版结果”是预设的，明确标注“示例”。
- 读者点击表格任一行，下方缩略图对应区域高亮。

### 2.5 小步 D：变成提示词

- 需求单五行自动组合成提示词，结构固定：

```
我想做一个个人主页，请先不要写代码，先告诉我你打算怎么做。

【给谁看】实习面试官，看完能通过邮件联系我。
【必须有】名字和一句话介绍；两个项目（名称、一句话说明、链接）；邮箱。
【这次不做】不用框架；只生成一个 index.html；不做暗色模式和动画。
【怎样算做完】电脑和手机宽度下都能完整显示、没有横向滚动条；邮箱链接能打开邮件应用。
【还不确定】头像先用占位；配色请给我两个方案选。

请列出：页面结构、要创建的文件、你需要我补充的信息。
```

- 最后一句“先不要写代码，先告诉我你打算怎么做”单独高亮，引出第 2 步“定计划”。
- 提供“复制提示词”按钮；同时提供“复制需求单（Markdown）”按钮，建议读者保存为项目里的 `需求单.md`——它在第 5 步还会被用来逐条检查。

### 2.6 完成依据

小步 D 底部：

- 示例结果（灰色标签）：需求单 5 项都已填写，其中“怎样算做完”有 2 条可检查的标准。
- 我做到了（读者勾选）：我在自己的 `my-homepage` 里保存了 `需求单.md`。

## 三、需求单在后续步骤中的“回响”

需求分析不能只在第 1 步出现。需求单作为一个**常驻对象**贯穿案例：

| 步骤 | 需求单怎么出现 |
|---|---|
| 2 定计划 | Agent 的计划逐条对应需求单；有一条计划写了“使用 Tailwind CDN”，与“不用框架”冲突，标红，示范如何回复“不要用 Tailwind，只写原生 CSS” |
| 3 生成并运行 | 文件树出现 `需求单.md` 和 `index.html` 两个文件 |
| 4 发现问题并修改 | 发现手机溢出时，需求单中“没有横向滚动条”一行闪烁：说明这是**没达到需求**，而不是新想法 |
| 5 检查并交付 | 检查清单直接由需求单的“必须有”和“怎样算做完”生成，逐条打勾 |

工作台右上角有一个“需求单”按钮（图标 + 文字），任何步骤都能打开侧边抽屉查看当前需求单，被引用的行高亮。

## 四、案例二的需求分析：在已有项目里改

案例二的第 1 步同样叫“想清楚”，但多了一个前置动作：**先读懂现有项目**。

- 场景：沿用现有素材，给一个已经能用的 Todo 应用（React + Express + SQLite）增加“任务备注”功能。
- 五问的变体：

| 五问 | 在已有项目里的问法 |
|---|---|
| 给谁看/要做什么 | 用户遇到了什么问题？改完后他能做到什么？ |
| 必须有 | 这个功能最少要包含哪些行为？ |
| 这次不做 | **哪些文件和功能不能动？** |
| 怎样算做完 | 哪些操作能证明它好了？原有功能是否还正常？ |
| 还不确定 | 现有代码里有哪些我看不懂、需要先问 Agent 的？ |

- 新增交互“先问再改”：第一条发给 Agent 的提示词是只读的——“请先阅读项目，告诉我数据是在哪里保存的，不要修改任何文件”。场景中 Agent 返回一张项目地图，读者在地图上点出“这次要改的地方”。
- 教学重点：**“这次不做”在已有项目中变成“不要动的范围”**，这是控制 AI 改动范围的关键。

## 五、速查页中的需求分析

`/guide/` 第一块就是“需求单五问”，包括：

1. 五问 + 每问一个好例子和一个坏例子。
2. 可复制的空白需求单模板（Markdown）。
3. “验收标准自查”：三条判断规则——别人能照着检查吗？能在页面上看到吗？有明确的数字或动作吗？
4. 好坏提示词对比（保留现有 ReviewPlayground 的 5 组，按五问重新归类）。

## 六、设计约束

- 需求拆解器的所有选项都是预设，不调用 AI，不上传输入内容；自定义输入只保存在本机浏览器。
- 读者可以跳过任意小步，也可以“一键填入示例答案”，避免卡住。
- 手机端：五问卡片全宽，需求单预览改为底部固定的“需求单（3/5）”条，点开为底部抽屉。
- 文字量控制：每张问题卡片的说明不超过 2 句，选项不超过 5 个。
